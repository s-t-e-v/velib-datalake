# Commit Policy

## Format

Follow Conventional Commits:

```
<type>: <short description>

<optional body: summary of changes or subtasks completed>
```

### Types
- `feat:` new feature
- `fix:` bug fix
- `refactor:` restructuring without behavior change
- `docs:` documentation only
- `chore:` tooling, deps, config
- `test:` tests
- `style:` formatting only

## Rules

- **Right-size your commits:** Commit cohesive, logical units of completed work. Avoid scattering micro-changes across a sea of tiny commits.
- **Keep the body simple:**
  - For small or single-purpose tasks, write a concise **single-line** subject and skip the body entirely.
  - Reserve the commit body for changes where additional context is useful, such as larger milestones covering multiple completed subtasks.
- **No vague messages:** Avoid lazy descriptions (`fix stuff`, `update`, `wip`).
- **No co-author lines:** Do not add agent/AI attribution (`Co-authored-by:`, `Generated by:`, or any equivalent).
- **Issue-closing work:** Put `Closes #<issue>` in the implementation commit message so GitHub closes the issue when it reaches the default branch. Keep follow-up policy or documentation edits in a separate commit.

## Examples

### Good (Small Change)
```text
fix: validate email domain before form submission
```

### Good (Milestone / Multi-task)
```text
feat: placeholder substitution before Gemini call

- Added sensitive field list to persona.ts
- Replaced phone, address, and email with placeholders before prompt construction
- Injected real values into LaTeX output post-generation
```

### Bad
```text
fix stuff
update gemini
wip: trying to fix latex
Co-authored-by: Claude <claude@anthropic.com>
```
